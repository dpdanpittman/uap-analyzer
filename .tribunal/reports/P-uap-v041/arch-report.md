# Tribunal Lens Review — Architecture · P-uap-v041 (verify-fix)

**Reviewer:** tribunal-reviewer-arch
**Verdict:** Approve

## Summary

All nine P-uap-v04 architecture findings the v0.4.1 patch claims to address close cleanly with precise, surgical edits and traceable hunks. The patch is a bug-fix, not a refactor: every new abstraction (`_MODEL_CACHE_LOCK`, `IMAGE_EXTS`, `VALID_HUD_MODELS`, `_VISION_JSON_MAX_BYTES`, `_hash_key`, `_bounded`, `_MAX_*`) traces back to an explicit P-uap-v04 finding. No untraceable hunks, no boundary breaches, no contract divergence. The cross-confirmed Critical (chdir race) is closed by passing an absolute path to `YOLO()` and serialising the entire load path under a `threading.Lock` — same lock pattern mirrored in `audio.py` for symmetry. One small architectural smell (unused return values on `_bounded()`) is filed as a Suggestion, not blocking.

## Regressions or new findings

### F-arch-101 — `_bounded()` return value is unused at every call site

- **Severity:** Suggestion
- **Location:** `src/uap_analyzer/server.py:32-39` and every `_bounded(...)` call site (`server.py:109-110, 143-144, 352-354, 404-405, 458-460`).
- **Hunk anchor:** v0.4.1 introduces `_bounded(name, value, cap) -> int | float | None` returning the value, but every caller discards the return: `_bounded("count", count, _MAX_SAMPLE_COUNT)` (statement form, return dropped). The function reads as if it clamps and returns the safe value, but actually it only validates+raises.
- **What:** Architecturally the helper is doing two things — validation (raises) and identity-pass-through (returns value). If a future caller writes `count = _bounded("count", count, _MAX_SAMPLE_COUNT)` thinking it will clamp to the cap, they'll get the same value back (the helper raises rather than clamps). Either the return is misleading, or the call-site convention is wrong. Today the behavior is correct (raise-before-dispatch), but the shape will bite a future maintainer.
- **Suggested defense:** Drop the return type — make it `def _bounded(...) -> None` — and the function name becomes a pure assertion (`_assert_bounded` would be even clearer). Alternatively, keep the return and assign at every call site so the intent is explicit.

### F-arch-102 — `_hash_key` duplicated across audio.py and detect.py

- **Severity:** Suggestion
- **Location:** `src/uap_analyzer/tools/audio.py:115-126` and `src/uap_analyzer/tools/detect.py:117-125`. flir.py inlines the same pattern at `flir.py:434-436, 439-441` (sha256[:16] of joined tuple).
- **Hunk anchor:** v0.4.1 introduces sha256 cache-key hashing across all three new tools (sec-F-sec-005) and implements it three times — twice as a `_hash_key` private helper, once inline.
- **What:** Three near-identical implementations of "sha256 the joined params". Not a correctness issue today, but the asymmetry (helper in audio + detect, inline in flir) reads as a half-finished extraction. If the hash format ever needs to change (e.g. bump from [:16] to [:32], or switch to blake2), three sites have to move in lockstep. Abstraction cost is low (one shared helper in `corpus.py` or a new `tools/_cachekey.py`).
- **Suggested defense:** Lift `_hash_key` to a shared module location (e.g. `src/uap_analyzer/tools/_cachekey.py` or a function on `Corpus`). Or inline all three. The current half-and-half is the architecturally inconsistent state.

### F-arch-103 — `_get_model` does double-validation against `VALID_MODELS`

- **Severity:** Suggestion
- **Location:** `src/uap_analyzer/tools/detect.py:78-80` (new) and `detect.py:61-64` (inside `_model_filename`).
- **What:** `_get_model` now explicitly checks `if name not in VALID_MODELS` and raises before taking the lock. `_model_filename(name)` (called inside the lock at line 99) does the same check. Both paths funnel through the same `VALID_MODELS` tuple, so behavior is correct, but the second check is dead. Not a defect — the new pre-lock check is the load-bearing one (avoid taking the lock just to immediately raise) — but the redundancy could be removed by stripping the check from `_model_filename`.
- **Suggested defense:** Drop the validation from `_model_filename` (keep the function pure: shortname → filename) and rely on the pre-lock check in `_get_model`. Cosmetic.

## Cross-Reviewer Ready Notes

- **For security reviewer:**
  - `_bounded()` accepts `bool` silently because `bool` is a subclass of `int` (`True < 0` → False; `True > 100` → False). The bool-guard pattern that fixes sec-F-sec-010 in `_normalize_vision_fields` is NOT mirrored in `_bounded()`. Today MCP tool signatures are typed (`sample_count: int`) so a JSON `true` likely gets coerced before reaching the helper, but the helper itself isn't defensive. Probably out-of-scope for sec but worth a glance.
  - `_VISION_JSON_MAX_BYTES = 64 * 1024` at `flir.py:312` is a soft cap — content is `[:N]`-sliced before parse rather than rejected. A truncated JSON will hit the `RecursionError`/`ValueError`/`TypeError` handler at `flir.py:356` and log + return empty, which is the right shape. Confirm the failure surface matches intent.
  - `f"unknown vision_model {resolved_vision_model!r}; valid: {sorted(VALID_HUD_MODELS)}"` at `flir.py:421-424` echoes the client-supplied string back in the error message via `repr`. `repr()` escapes control chars but a long client-controlled string in an error message has historically been a CRLF/log-injection vector. Probably fine here (no log forwarding to syslog) but flag for sec lens.
  - The new `IMAGE_EXTS` classifier at `detect.py:194` reads only the suffix. A file named `evil.png.mp4` (multi-extension) classifies as video (correct — `.suffix` returns `.mp4`). A file `evil.png` containing video bytes classifies as image and ffmpeg-skipped → goes straight into YOLO. YOLO will fail on a non-image input but the failure mode flows back through the executor. Probably acceptable.

- **For performance reviewer:**
  - `_MODEL_CACHE_LOCK` is held across the YOLO load (which is the cold-start download path, ~30-90s for the first call). Concurrent first-calls for _different_ models will serialize, not parallelize. For the current single-operator workflow this is fine; flag as a future improvement (could split the lock per-model name).
  - The `_get_model` pre-lock validation at `detect.py:78-80` is a micro-optimisation (avoid taking the lock just to raise). Worth verifying: under contention, does the pre-lock raise actually help latency, or is the contention dominated by the cold-start download? Probably the latter.
  - The `_hash_key` sha256 cost is microseconds per call but it's now in the cache-miss hot path. Profile if cache hit ratio drops noticeably between v0.4.0 and v0.4.1 (a separate concern — the v2 cache-key prefix means all v1 entries are orphaned, so the first session post-deploy has a 100% cache miss until the new entries populate).
  - The vision-mode hoist at `flir.py:465-468` correctly preserves TCP keepalive across frames within one `flir_hud_ocr` call but each invocation still builds a fresh `OllamaClient`. For a workflow that calls `flir_hud_ocr` repeatedly on different videos, the client churn is still there — flag for a future `cfg`-scoped client cache if that workflow becomes common.

## Verdict rationale

All 9 architecture-lens findings from P-uap-v04 are closed (8) or deferred-by-design (1). The patch introduces no new boundary breaches, no new abstractions without payoff, and no untraceable hunks. The cross-confirmed Critical (chdir race) is closed with the exact fix the architecture lens recommended (`YOLO(str(weight_path))` + `threading.Lock`). Three Suggestion-level architectural smells (unused return on `_bounded()`, duplicated `_hash_key`, redundant validation in `_get_model`/`_model_filename`) are noted but non-blocking — they're polish, not defects.

**Approve.**
